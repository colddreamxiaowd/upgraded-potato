# Agent Watchdog：独立监督与软件验收产品计划书（审稿稿）

> **版本**：v0.1 / 2026-10-12  
> **状态**：PROPOSAL / REVIEW REQUIRED（不是开发授权，也不是产品效果证明）  
> **适用对象**：Windows 11 上使用 Codex 等编码 Agent 的个人开发者；先聚焦单人、本地、长任务。  
> **文档性质**：面向独立审稿人的产品假设、竞品证据、实验设计和阶段决策书。  
> **重要说明**：本仓库刚初始化，没有 Agent Watchdog 的实现、性能结果或用户验证数据。本文不应被理解为已经完成软件开发、跑过对照实验或确认创新性。

## 0. 执行摘要

**拟解决的问题**：编码 Agent 长时间自主开发时，用户不能持续盯屏；Agent 的“完成”声明、绿色测试、Git 提交和真正满足原始需求，可能不一致。已有开源工具覆盖了日志追踪、停滞检测、执行监督、测试新鲜度、验收合同、测试重跑等大量功能。因此，**我们不以“再做一个 Agent 监控器”为产品定位**。

**待验证的产品假设**：对 Windows + Codex 的个人开发者，能否用一个低侵入、本地优先的工具，将 **持续监督 + 可追溯证据 + 基于原始需求的独立软件验收** 连成一个易用工作流，并在真实缺陷检出、误报、配置成本和人工省时方面，相比直接组合既有工具取得可观察优势？

**当前建议：RESEARCH GO / PRODUCT HOLD**。允许开展限量竞品复核与探索性验证；在获得对照结果和真实用户信号前，不授权做大而全的平台、不宣称填补市场空白、不宣称商业价值已经成立。

**首轮最重要的三条判定问题**：

1. 直接使用 dotpals + proof-of-done + proof-of-work 等开源方案，是否已经足够解决目标用户问题？
2. 在项目现有测试缺失、不完整或被削弱时，新增验收机制能否独立发现用户可观察的实际缺陷，而非只生成“看起来很专业”的报告？
3. 引入监督器后，用户整体时间与风险是否下降，还是被错误告警、复杂安装和审计运行本身的副作用抵消？

## 1. 背景、用户与产品边界

### 1.1 初始用户与场景

目标用户暂定为：使用 Windows 11、Codex、Python/本地 IDE/Git，偶尔将数小时的开发任务交给 Agent 的独立开发者。典型场景：

- Agent 长时间无可见进展，用户不知道它是在正常计算、工具阻塞还是陷入循环。
- Agent 报告“已完成”，但某项功能在真实软件中不可用，或修改导致回归。
- 任务在会话重启、上下文压缩、交接之后发生需求漂移。
- 已有测试被跳过或削弱，用户不知情；审计工具又可能误把测试通过理解为功能正确。
- 用户希望只在需要注意时收到 **有证据、可复查、可解释** 的提醒，不接受监督器擅自删除文件、终止进程或改写代码。

### 1.2 产品不做什么

第一版明确**不做**：

- 通用 LLM trace/observability SaaS（优先参考 Langfuse 等成熟平台）。
- 面向所有平台、所有 Agent、所有语言的统一接入。
- 自主修改项目、自动合并 PR、无人确认地执行高风险恢复。
- 以“无文件写入 N 分钟”直接断言 Agent 卡死；以“测试通过”断言用户需求完成。
- 绝对正确的代码安全证明、通用 GUI 代理、全面安全审计或生产上线批准。
- 在未经实际安装和实验验证前宣传“优于现有开源方案”。

### 1.3 可检验的价值主张

候选表述：**不用时刻盯着 Codex；异常时给出证据，完成时给出哪些需求被独立验证、哪些尚未验证的清单。**

该表述只有在第 6 节探索性试验及第 7 节用户研究通过后，才有资格转化为正式产品承诺。

## 2. 竞品与开源复用调研

### 2.1 调研方法与证据等级

本轮（2026-10-12）通过 GitHub 仓库元数据与项目 README 复核下列主要竞品的存在、描述、开源许可证及公开功能。**没有逐一安装、运行、做代码安全审查、测量真实性能**。功能描述属于“上游项目公开声明”，不等于我们已独立复现。

证据分级：

- **E1 已直接复核**：仓库元数据、README 中明示的功能或限制。
- **E2 分析性判断**：基于项目定位推断的待验证差距，不能写作“竞品没有此能力”。
- **E3 未经测试的假设**：目标用户需求、实际质量改进、误报率、性能或收益。

后续所有竞品比较都要记录：访问日期、仓库 URL、被检版本/提交、README/实现证据位置、可复现命令、许可证、限制及适用环境。**禁止把缺失的 README 描述当成证实缺少功能。**

### 2.2 核心竞品对照（公开能力，不是跑分）

| 项目及仓库 | 已核对的公开能力（E1） | 与拟议产品的关系 / 下一步验证 |
|---|---|---|
| [dotpals](https://github.com/Rikinshah787/dotpals) | 支持 Codex/Claude 等，多端安装、测试状态与新鲜度、疑似假通过提示、会话交接、MCP、通知 | **最重要的产品体验对照基线**。必须实际验证其现有能力是否已足够，不能轻易宣称“没有验收”。 |
| [Foreman](https://github.com/thruwire/foreman) | 监督 worker、诊断进展和偏离、启动独立 verifier；README 指出当前一次运行一个 worker | **语义监督直接竞品**。需实测误报、介入成本与目标正确性；不能因为它有模型判分就视其为有效。 |
| [proof-of-done](https://github.com/lykAntonio/proof-of-done) | 提前制定验收合同、事后审计、重验、明确 UNKNOWN/HUMAN_REVIEW；承认不能替代产品判断/CI/安全审查 | **验收协议优先参考对象**。独立实验前优先比较直接使用其工作流的收益。 |
| [Proof-of-Work](https://github.com/Rajveerx11/proof-of-work) | 重跑真实测试、检查测试篡改与削弱、证据日志；README 明确某些严格源代码策略与发布版不同 | **确定性验证对照基线**。需区分已发布能力和未发布分支，不宣传未经复现的检测效果。 |
| [codex-task-watchdog](https://github.com/TanChuping/codex-task-watchdog) | Windows-first，Codex 日志/流停滞诊断、通知与交接；README 提醒本地 Codex 日志格式会变化 | **Windows 采集和停滞监控对照**。优先考虑适配而不是重写，验证兼容性与许可。 |
| [codex-watchdog](https://github.com/elgabrielc/codex-watchdog) | Git worktree、分支/祖先检查、路径规则、停滞/例外报告；README 表明不解析完整 Codex 会话内容、Windows 未测试 | **Git 不变量规则参考**。不是端到端功能正确性基线。 |
| [claudewatch](https://github.com/blackwell-systems/claudewatch) | Claude Code 错误循环、漂移信号、上下文压力、成本与 MCP/Hook 分析 | **启发式误报参考**；连续阅读文件不等于偏离，需人工标签校准。 |
| [BuilderIO agent-watchdog skill](https://github.com/BuilderIO/skills/blob/main/skills/agent-watchdog/README.md) | 基于会话/PR/分支审计声明、diff、测试、CI、截图并形成 gap report | **任务结束后审计对照**；需进一步验证是否能够持续、低侵入监督。 |
| [AI Project Dashboard](https://github.com/hpigu/AIProjectDashboard) | 本地优先、多 Agent 任务板、依赖与完成证据记录 | **任务契约和交接参考**；不是直接的业务验收性能证明。 |
| [Langfuse](https://github.com/langfuse/langfuse) | 开源 Agent observability、trace、评估及反馈 | **避免重造追踪基础设施**；与本地编码任务独立验收不完全同一产品类别。 |
| [Invariant Guardrails](https://github.com/invariantlabs-ai/invariant) | Agent 工具调用安全规则/guardrail | **行动安全层参考**，不等于最终交付验收。 |

GitHub 仓库元数据已核对：上述项目均可访问，部分更新很近，公开功能可能随时变化。许可证以本轮仓库元数据为准；**代码整合前必须再次核对目标提交的 LICENSE、依赖和第三方代码许可**。例如 Langfuse 的 GitHub license 元数据未给出单一可直接确认的 SPDX 许可，不应据此武断当成可任意复制的 MIT 库。

**Gitee 补充要求**：上一轮调研曾记录 [NovaAgent](https://gitee.com/agent-dev-team/nova-agent) 和 [AgentScope-Studio 的 Gitee 镜像](https://gitee.com/chumingjuncn/agentscope-studio) 等邻近项目，但本次上传前未重新独立复核其版本与功能，因此标为 **待核实线索**，不纳入已经实测的基线或“国内竞品不足”结论。下一轮检索应补齐其维护状态、许可证与可用模块。

### 2.3 不允许作为“独创点”的通用能力

仅凭下列能力不能构成差异化结论：收集日志、展示 Agent 状态、检测重复错误、检查 Git 越界、读取测试报告、判断测试是否过期、宣称检测跑偏、生成审计报告、要求完成证据、定义 UNKNOWN。它们都已有公开竞品覆盖或部分覆盖。

**真正需要验证的不是功能清单更长，而是同样任务下是否更可信、更省心、更易部署。**

## 3. 待证伪的产品假设及竞争解释

| 编号 | 假设（不是事实） | 竞争解释 / 可否定原因 | 所需证据 |
|---|---|---|---|
| H1 | “持续监督 + 独立验收”的组合比直接使用现有工具更有用 | dotpals + proof-of-done + proof-of-work 已足够，额外外壳只是增加摩擦 | 同任务、同环境、同资源约束下的基线对照 + 用户体验记录 |
| H2 | 没有完善既有测试的任务，也可以产生可靠的外部验收 | 系统可能只能重复原 Agent 的猜测；生成测试可能复制原错误假设 | 独立人工预设 oracle + 可复现的黑箱功能验证 |
| H3 | 监督器能少打扰用户且及时指出真实问题 | 语义误报造成频繁打断，得不偿失 | 事件级误报、漏报、每任务告警量、人工处理时间 |
| H4 | Windows 本地零/低配置是明显优势 | 现有 dotpals 已支持 Windows 且安装简单，难以形成优势 | 两台以上真实 Windows 设备上的安装/复现对比 |
| H5 | 证据契约提高跨会话验收的一致性 | 人工确认契约成本很高；验收条件本身可能被错误生成或任务中途变化 | 固定任务变体下，结果重现与 contract drift 核验 |
| H6 | 个人开发者愿意持续使用 | 用户只是觉得报告有趣，并不会真的节省时间或更频繁启动工具 | 真实使用/试用访谈、留存意愿和付费意愿（分别测量） |

**替代路线必须同时参与竞争**：如果“只装 dotpals，必要时运行 proof-of-done / Proof-of-Work”已经满足主要要求，优先写组合教程/薄适配层，**不开发新平台**。

## 4. 拟议最小产品：任务契约 + 事件证据 + 独立验收

### 4.1 最小闭环

1. **输入原始任务**：原始用户要求、仓库位置、目标分支、运行命令、用户允许的权限与风险边界。
2. **生成候选验收合同**：将任务分为可观察的 PASS/FAIL 条件、需要人工判断的条件和无法安全检测的条件。对高风险/模糊的验收条件先人工确认；合同需版本与散列。
3. **采集事实**：进程/会话事件（若可用）、工作树与提交变化、执行命令和退出码、测试日志、构建产物与运行结果。采集失败应单独记录。
4. **按风险触发验证**：优先确定性检查（Git、测试重跑、接口/CLI 黑箱断言），无法验证时 UNKNOWN；不得把“大模型判断可信”作为唯一来源。
5. **独立报告**：每条用户要求对应 verdict、证据路径、复现命令、源代码版本、运行环境、时间和未覆盖风险。
6. **人工处置**：向用户显示必要告警与最终报告；默认仅提示，不自动修改代码、重置 Git 或终止进程。

### 4.2 分层结构（建议而非已实现）

- **采集适配层**：Codex-first，避免依赖单一非稳定日志格式；插件接口可以新增其他 Agent。
- **事实记录层**：本地事件索引 + 内容哈希 + Git SHA + 工具版本 + 时间戳；有缺口时标为“证据缺失”。
- **验收契约层**：原始要求、验收项 ID、证据类型、风险级别、合同修订历史。
- **验证执行层**：只读静态检查、受限测试重跑、隔离式接口/UI 测试；执行本身记录副作用和退出码。
- **决策层**：规则优先；可选语义辅助只提出“待查疑点”，不得覆盖确定性证据。
- **本地呈现层**：只展示值得注意的事件、任务状态、PASS/FAIL/UNKNOWN/HUMAN_REVIEW 及复现入口。

### 4.3 判定规则（必须写进协议）

| 状态 | 准入条件 | 明确禁止的推断 |
|---|---|---|
| PASS | 与固定验收项直接对应的、可复现、近期且成功的验证证据 | 不能扩大成“整个项目正确” |
| FAIL | 可复现的反例或违反明确不变量的直接证据 | 不能仅凭模型怀疑就 FAIL |
| UNKNOWN | 证据缺失、环境不可用、结果含糊、安全边界阻止验证 | 不能默认为 PASS 或 FAIL |
| HUMAN_REVIEW | 主观体验、业务政策或需要人类决策 | 不能用未经校准的模型评分替代人工 |

“测试已运行”不等于“测试针对最新修改”；“正确定位按钮”不等于“用户任务成功”；“10 分钟没有新文件”不等于“阻塞”。每个结论必须限定其证明范围。

### 4.4 安全边界

**默认无代理执行权**。首版禁止自动修改代码、删除文件、推送远程、联网发送日志、后台任意执行未审核脚本。需要运行受测仓库的测试或应用时，使用隔离工作树/临时副本、权限限制、超时、资源上限与敏感信息脱敏；无法建立安全隔离时，报告 UNKNOWN 并请求用户手工验证。任何凭据与敏感日志不得进入外部模型。

威胁模型同时覆盖 **被监督 Agent、项目文件、测试脚本、日志/工具输出和审计模型本身**。项目文件里的文字视为待检查数据，不能提升为审计器指令。日志不可信；弱信号只能用于提醒，不得自动触发破坏性恢复。

## 5. 项目路线与阶段门槛

> 以下为拟议范围和粗略工作包，不是已经实现的版本、工期承诺或实施授权。

### P0 — 现有开源方案可用性核查（先做）

- 对 dotpals、proof-of-done、Proof-of-Work、Foreman、codex-task-watchdog 做可安装性、Windows 兼容性及基本安全性检查。
- 固定上游提交 SHA、LICENSE、安装步骤；最少覆盖“正常完成”“明确缺陷”“证据不足”三个案例。
- 先制作 **无需开发新产品的组合方案**；记录是否已能完成最终用户需求。
- 输出：复现手册、竞品运行对照表、可信来源索引、复用 / 不复用决议。

**Gate P0**：如现有工具组合已基本解决问题，停止新平台开发，仅整理集成/教程/必要适配器。不可因“想做自己的项目”越过此门槛。

### P1 — 最小独立验收器（仅在 P0 未解决时）

- 先支持 Python 项目的 CLI 或本地 Web 服务二选一，不兼容所有项目类型。
- 读取固定验收合同，读取独立测试结果并记录证据；支持 4 类判定。
- 完成“正常 / 明确错误 / 无法验证”的演示，覆盖输入异常、测试超时和权限不足。
- 仅允许只读/隔离执行，无需 UI 花活。

**Gate P1**：验收结果能由第三方按报告复现；不能确定时不会假报成功；风险边界无明显穿透。

### P2 — Codex 监督适配与用户提醒

- 接入受支持的 Codex 事件、Git 变更和验收合同。
- “长时间无进展”仅触发人工复核建议；区分静默工具、编译、正常长计算与日志中断。
- 摘要只展示“发现什么 + 证据 + 建议下一步”，减少刷屏。

**Gate P2**：同一套数据下，误报率、漏报率和打扰成本不逊于基线；否则保留验收工具、不做实时监督。

### P3 — 真实试用与继续/停止决策

- 邀请至少数名真实 Codex 使用者尝试常见任务；记录初次配置、误报、节省的手动核查时间及“不再使用”的原因。
- 如价值不明显，退回工具组合教程或独立审计 CLI；不要无期限追加功能。

## 6. 探索性比较实验（设计草案；结果尚不存在）

### 6.1 待回答的研究问题

在相同的编码任务交付件上，我们能否相对于 **不使用审计 / 直接使用成熟工具组合**，以可接受的误报和运行成本，可靠发现用户可观察的功能缺陷和证据不足？

### 6.2 基线与实验组

- **B0：人工常规检查** —— 阅读 Agent 完成声明、查看 diff 和现有测试摘要。
- **B1：现有工具组合** —— 按可用性/许可选择 dotpals + proof-of-done + Proof-of-Work；如某工具环境不兼容，明确标注，不强行凑齐。
- **B2：现有语义监督方案** —— 若 Foreman 可在同等条件下运行，单列比较其告警，不将语义概率当真值。
- **C：我们的最小闭环** —— 只有 P1/P2 实际实现后才能入组；不能用提示词模拟结果冒充已运行产品。

同一测试任务、相同可用信息、相近验证预算与固定代码快照；检查是否所有工具都获准访问相同材料。不能把“没有接口可接入”与“检测能力差”混为一谈。

### 6.3 样本构造

**建议先做 12 个代表性开发任务 × 3 种交付状态 = 36 个探索性案例**，其中每类 12 个：

1. **满足验收的交付**：防止任何修改都被误认为风险。
2. **注入且可复现的用户可观察缺陷**：如错误边界处理、回归、权限/校验错误、页面流程断裂。
3. **证据不足或不可安全验证**：故意缺失依赖、没有预定义 oracle、重要业务条件模糊，检查工具能否输出 UNKNOWN/HUMAN_REVIEW 而非自信通过。

任务覆盖 CLI/API、简易 Web UI、数据处理、现有项目回归四类；避免全部来自同一个 toy app。缺陷由独立评审预先定义，并用可执行 oracle / 手工重现步骤确认。验收合同和判定标准在查看实验组输出前冻结。

**局限**：36 例只能说明该受控任务集合内的探索性表现，不能推断所有编码语言、Agent、开发者或真实项目的通用可靠性。不得将重复变体视为独立总体样本。

### 6.4 指标与分母

| 指标 | 计算方式或记录方法 | 防止的误解 |
|---|---|---|
| 缺陷检出率 | 找到预先确认缺陷的案例数 / 有缺陷案例数 | 不能把含糊提醒都算检出；需定位可验证问题 |
| 误阻断率 | 无缺陷案例中产生明确错误阻断的例数 / 无缺陷案例数 | 正常长任务不能被误报为失败 |
| 正确不确定率 | 证据不足案例正确标为 UNKNOWN/HUMAN_REVIEW / 不足案例数 | 模型自信地猜对不算可验证 |
| 可复现证据率 | 另一位审稿人按记录成功复核的明确裁决数 / 所有明确裁决数 | 避免只有漂亮评分却不能复核 |
| 告警负担 | 每任务通知数、被用户判为无用的比例、处理分钟数 | 避免“发现得多”但打扰更大 |
| 延迟/成本 | 额外运行时间、CPU/内存、模型 token/API 支出 | 防止自动审核成本高于人工 |
| 配置成功率 | 独立 Windows 环境在无作者远程帮助情况下完成安装的比例与耗时 | 不把开发者本机成功当易用性证明 |

所有分母、失败数据和未支持场景必须完整披露。标签人员尽量不看系统预测结果，避免事后改变 oracle。对比采用原始逐案例记录，不以单个综合分遮盖互相冲突的结果。

### 6.5 初步判定阈值（需在第一次实验前预注册）

建议仅作为**讨论中的候选门槛**：在 12 个注入缺陷案例里至少给出 10 个具有可复现证据的有效发现；在 12 个正确交付中明确错误阻断不超过 1 个；在 12 个证据不足案例中至少 10 个正确维持不确定状态；任何未经授权的破坏性操作为零。还需满足：与最强可安装开源组合相比，至少在一个事先定义的用户价值指标上呈现明确优势，且其他核心指标不显著恶化。

这些 **不是统计显著性标准，也不是业界共识**。12 例分辨率较粗，任何达标只能授权更广的独立复验，**不能直接宣布产品可靠或具有商业价值**。若没有给出公平、可执行的验收门槛，应先冻结定义再开始实验。

### 6.6 失败与回退

- 发现只是重新包装现有开源组合 → **STOP 原平台构想，写集成层/教程**。
- 高误报或人类看报告的时间增长 → **缩减到“结束后审计”而不是实时监控**。
- 缺陷检测依赖原 Agent 自述 → **拒绝效能结论；增加独立 oracle 或标 UNKNOWN**。
- 隔离测试无法安全运行 → **禁用自动执行，明确人工验证路径**。
- 数据不足或偏向单一任务 → **仅报告探索性结果，不升级广泛可靠性声明**。

## 7. 用户痛点与数据可得性（必须与技术验证分开）

尚未证明目标人群愿意安装或持续使用该工具。优先公开收集并归档可核验的现实痛点信号（GitHub Issues、社区帖子、已有产品评论），注意去重、样本偏倚及用户许可；**不能将开发者自我宣传或演示当作付费需求**。

随后寻找约 5 位实际使用 Codex 或同类编码 Agent 的外部用户，观察以下真实操作：如何发现“完成但不可用”、是否愿意填写验收合同、是否会读报告、何种告警有价值、最不能接受的权限和成本。5 人是定性探索，不作市场占有率或总体比例推断。

数据可得性风险：

- Codex 本地事件结构可能改变，取不到完整数据。
- 无真实测试的项目缺少可信 oracle。
- 开源工具能力和上游实现快速迭代，静态竞品表会过时。
- 真实用户代码常含机密，不得为了调研上传源码/日志。
- Agent 长任务的故障复现成本高，样本可能偏向人为种下的简单 bug。

**用户研究的否定性结果同样有价值**：例如用户对工具无感、安装阻力过大、真正痛点是需求不明确而非监督缺失，均应触发产品方向调整。

## 9. 主要风险清单

| 风险 | 优先级 | 防范与停机条件 |
|---|---|---|
| 与 dotpals / proof-of-done / Foreman 等高度重复 | 极高 | P0 先实测现有方案；已有方案能覆盖就不重复造平台 |
| 验收 oracle 错误或不独立 | 极高 | 冻结合同、独立复核；无法确定输出 UNKNOWN |
| 监督器执行恶意/破坏性测试 | 极高 | 隔离、最小权限、测试审批；无法保证则不执行 |
| 告警噪声与模型误报 | 高 | 弱信号不自动阻断；每类告警单独统计误报 |
| Windows / Codex 日志兼容性变化 | 高 | 适配层、能力检测、优雅降级，不把静默等同卡死 |
| 私有源码、密钥或日志泄露 | 高 | 本地优先、默认脱敏、不自动外传、用户明确授权 |
| 为展示创新而不断扩大范围 | 高 | 每阶段设置具体 Gate；NO-GO 可以终止路线 |
| 用户渠道不足或无真实需求 | 高 | 早做真实使用观察，不用 GitHub Stars 代替价值验证 |

## 10. 独立审稿请求（请优先反驳）

请审稿人尽量不要只评价“计划完整不完整”，而要回答可直接导致本项目停止或改道的问题：

1. **撞车审查**：是否存在比文中更直接、更成熟的同类产品？请给仓库/产品链接、具体功能及复现实例。
2. **必要性**：在 dotpals + proof-of-done + Proof-of-Work 已存在的前提下，新项目剩下的可检验价值到底是什么？应否直接停止做独立产品？
3. **实验有效性**：36 个探索性案例、三状态变体、独立 oracle、基线的信息权限是否公平？哪里可能发生数据泄漏或偏向？
4. **自我审计陷阱**：生成验收测试的模型是否会重复编码 Agent 的错误需求理解？如何在资源有限时降低风险？
5. **安全**：执行未知仓库测试代码的隔离边界是否足够？哪些风险应当直接让系统不执行？
6. **产品聚焦**：最小有价值交付应是 Codex 监督、结束后验收、还是现有开源组件整合？只能保留一项时选哪个？
7. **现实用户**：哪些细分用户确实频繁遇到该问题？能否找到公开且可核验的抱怨/支付/替代方案证据？
8. **终止标准**：什么实验结果足以建议 NO-GO？当前门槛是否过于宽松或缺乏分母？
9. **许可与维护**：被建议复用的上游代码在版本/许可证/维护上有哪些被忽略的限制？
10. **未证实断言**：全文哪一句把推论写成了事实？请指出具体段落并给修正建议。

**期望审稿输出格式**：结论 GO / REVISE / NO-GO；最严重的 3–5 个问题；可核验证据链接；替代路径；建议的下一次最小验证。欢迎逐行评论、反例与否定性意见。
